# Erney's Translate Tool — разбор кода и план улучшений

> Разобран коммит `ceea95f` (v1.0.29, ветка `main`), ~12,7 тыс. строк C#.
> Разбор статический: приложение не собиралось и не запускалось (WPF/Windows).
> Номера строк указаны для этого коммита. Где вывод нужно подтвердить на
> Windows, это помечено **«Проверить»**.
>
> Оценка сложности: **S** — до пары часов, **M** — день-два, **L** — больше.

---

## Коротко

Архитектура понятная, комментарии отличные. Нашлось несколько реальных
багов, и минимум два из них, по-моему, напрямую участвуют в мерцании.
Самое важное:

1. Весь пайплайн (захват → OCR → перевод), судя по коду, выполняется на UI-потоке.
2. Во время перевода оверлей перерисовывается неполным списком регионов —
   остальные таблички на это время пропадают.
3. DPI нигде не учитывается — при масштабе 125/150% оверлей съедет.

## 1. Баги (по убыванию важности)

### 1.1. Пайплайн на UI-потоке — S–M
- [ ] Сделано

**Где:** `Core/CaptureService.cs:61` (`_captureTask = CaptureLoopAsync(...)`),
`:111`, `:131`, `:137` (`await Task.Delay(...)` без `ConfigureAwait(false)`).

**Что происходит:** `ToggleEngineAsync` вызывается из команды на UI-потоке →
`StartCaptureAsync` запускает цикл напрямую, без `Task.Run`. Каждый
`await Task.Delay` захватывает `DispatcherSynchronizationContext`, и
продолжение возвращается в WPF-диспетчер. В итоге на UI-потоке выполняются
`PrintWindow`, 4096 вызовов `GetPixel` (`TranslationEngine.cs:847-864`),
кодирование в PNG и инференс PaddleOCR. Главное окно и оверлей тормозят.

Комментарий в `ViewModels/ProfilesViewModel.cs:48` («StartAsync runs on a
worker») этому не соответствует.

**Проверить:** залогировать `Application.Current.Dispatcher.CheckAccess()` и
`Environment.CurrentManagedThreadId` в начале `OnFrameCaptured`.

**Исправление:**
- запускать цикл в фоне: `_captureTask = Task.Run(() => CaptureLoopAsync(ct))`
  (или отдельный поток с `LongRunning`);
- в `OverlayManager` заменить `Dispatcher.Invoke` на `BeginInvoke`
  (с объединением: если предыдущее обновление ещё не отрисовано, заменять его,
  а не ставить в очередь);
- проверить, что все обработчики `StatusUpdated` / `StateChanged` в VM
  маршалят на UI-поток.

### 1.2. Зависание при выходе во время перевода — S
- [ ] Сделано

**Где:** `Core/TranslationEngine.cs:879` (`StopAsync().GetAwaiter().GetResult()`
в `Dispose`), вызывается из `App.OnExit` → `Services.Dispose()`.

**Что происходит:** UI-поток синхронно ждёт остановки цикла захвата, а
продолжение отменённого цикла (из-за п. 1.1) стоит в очереди того же
UI-потока → вероятная взаимная блокировка. Процесс остаётся висеть после
«Выход» из трея и перед установкой обновления (`RealExit` в
`MainWindow.xaml.cs:198`).

**Проверить:** запустить перевод → «Выход» в трее → диспетчер задач.

**Исправление:** вместе с п. 1.1; дополнительно — останавливать движок
асинхронно в `RealExit` до `Application.Current.Shutdown()`.

### 1.3. Неполный список регионов при сетевом/потоковом переводе — S
- [x] Сделано (v1.0.30)

**Где:** `Core/TranslationEngine.cs:400-406` (`OnRegionUpdated` передаёт
`partial`), `Views/OverlayWindow.xaml.cs:238-248` (удаляются таблички,
которых нет в списке).

**Что происходит:** пока идёт запрос по одному региону, таблички всех
регионов, до которых очередь ещё не дошла, удаляются с канваса и потом
создаются заново. Видно как мерцание при каждом сетевом запросе.

**Исправление (варианты):**
- во время перевода передавать в оверлей полный список: для ещё не
  обработанных регионов — то, что уже на экране;
- или для промежуточных обновлений не удалять «лишние» таблички (флаг
  `isPartial` в `SetRegions`), удалять только при финальном рендере.

### 1.4. DPI не учитывается — S
- [ ] Сделано

**Где:** `app.manifest` (PerMonitorV2), `Views/OverlayWindow.xaml.cs:71-74`,
`:187-188`, `:232-233`, `OverlayWindow.UpdateBounds`.

**Что происходит:** физические пиксели из `GetWindowRect` и координаты OCR
записываются в `Left/Top/Width/Height` и `Canvas.SetLeft/SetTop`, а WPF
считает их в DIP. Пересчёта DPI в коде нет ни одного. При масштабе ≠ 100%
окно оверлея растянется, таблички сместятся.

**Проверить:** Windows → Параметры → Экран → масштаб 125% или 150%.

**Исправление:** получать DPI монитора целевого окна
(`VisualTreeHelper.GetDpi(overlay)` или `GetDpiForWindow(hwnd)`) и делить
все координаты на `DpiScaleX/Y`; либо брать
`PresentationSource.FromVisual(overlay).CompositionTarget.TransformFromDevice`.
Учесть переезд игры на другой монитор (событие `DpiChanged`).

### 1.5. Перевод висит, когда текст исчез — S
- [x] Сделано (v1.0.30)

**Где:** `Core/TranslationEngine.cs:345` (`if (rawRegions.Count == 0) return;`),
`:411` (`if (translated.Count == 0) return;`), `:510` (reuse рисует весь
снимок).

**Что происходит:** если текст пропал (закрылось окно диалога, показ CG),
оверлей продолжает показывать старый перевод до появления нового текста.
Reuse при этом рисует и те регионы снимка, которых в новом кадре нет.

**Исправление:** счётчик пустых кадров; после N подряд (~0,5 с, т. е. 2–3
кадра) — `_overlay.Hide()` / очистка. В reuse рендерить только те
переведённые регионы, которые пересекаются с найденными сейчас.

### 1.6. Гонка в PaddleOCR (возможное падение процесса) — S
- [ ] Сделано

**Где:** `Core/Ocr/PaddleOcrBackend.cs:194` (снимок списка движков под
блокировкой), `:222` (`engine.Run` уже без неё), `:164-169` и `:321`
(движки уничтожаются под блокировкой).

**Что происходит:** если во время распознавания завершилась переинициализация
(смена языка/профиля) или вызван `Dispose`, нативный движок уничтожается
прямо во время `Run` → обращение к освобождённой памяти.

**Исправление:** держать `_swapLock` на всё время распознавания (или счётчик
ссылок и отложенное уничтожение).

### 1.7. SQLite-кэш: одно соединение на несколько потоков — M
- [ ] Сделано

**Где:** `Data/CacheRepository.cs:37` (одно `SqliteConnection`), `:81-99`
(чтение без блокировки), `:282-306` (транзакция + `VACUUM` под блокировкой
записи в фоне).

**Что происходит:** `SqliteConnection` не потокобезопасен. Пока у соединения
открыта транзакция вытеснения, команды без неё падают → ложный промах кэша →
лишний запрос к API. `VACUUM` на большой базе (до 1 ГБ) держит блокировку
записи секунды — кадр в это время стоит.

**Исправление:** `PRAGMA journal_mode=WAL`; отдельное соединение на операцию
(пулинг в Microsoft.Data.Sqlite включён по умолчанию) или общая блокировка;
`PRAGMA auto_vacuum=INCREMENTAL` + `incremental_vacuum` вместо полного
`VACUUM`. Мелочь: индекс `IX_Cache_Text` дублирует индекс от `UNIQUE`.

Проверить остальные репозитории (`HistoryRepository`, `GlossaryRepository`,
`GameProfileRepository`) на ту же схему.

## 2. Мерцание склейки — что нашёл и план

### Причины, видимые в коде
1. **Неполный список при переводе** — п. 1.3.
2. **Reuse слишком строгий:** каждый новый регион обязан найти пару
   (`TranslationEngine.cs:505`). Один шумовой регион на фоне — reuse не
   срабатывает, идёт полный пайплайн с риском переиграть склейку.
3. **Табличка опознаётся по `OriginalText`** (`OverlayWindow.xaml.cs:44, :91,
   :184`): при «склеено ↔ разорвано» ключи меняются, таблички пересоздаются,
   «липкие» позиции теряются.

### План (от дешёвого к дорогому)
- [ ] **2.1. Инструмент записи и прогона.** Флаг в настройках «записывать
  OCR»: каждый кадр → строка JSONL (`bounds`, `text`, `score`, время).
  Вынести группировку + reuse + стабилизацию в чистый класс без WPF и
  написать тест, который прогоняет запись (например, сцену из Yankee
  Massage) и считает число смен раскладки на статичной сцене. Цель — 0.
  Каждая следующая попытка проверяется за секунды, а не релизом.
- [ ] **2.2. Починить п. 1.3.**
- [ ] **2.3. Reuse по словам всего кадра.** Склеить текст всех регионов в
  порядке чтения, нормализовать (регистр, пунктуация, пробелы), разбить на
  слова и сравнить со снимком по доле совпавших слов (≥ 90%) + проверить, что
  общая рамка текста пересекается со снимком. Это не зависит ни от склейки,
  ни от шумовых регионов. Это урок провала v1.0.26 («сравнивать нужно по
  словам, а не по регионам»), но на входной стороне — та уже доказанно
  дружит со стримингом (v1.0.25).
- [ ] **2.4. Задержка перед сменой раскладки.** Если текст тот же (по 2.3), а
  группировка другая — применять новую, только если она повторилась в 2
  кадрах подряд. Если текст реально сменился — сразу.
- [ ] **2.5. (если не хватит)** Стабильные «слоты» в оверлее: отслеживать
  таблички по пересечению рамок между кадрами (IoU), а не по тексту; текст
  внутри слота обновлять на месте.

**Честно:** 2.2–2.3, по-моему, закроют основную часть случаев, но это
гипотеза, пока её не подтвердит прогон на записи из 2.1.

## 3. Производительность

- [ ] **3.1. Убрать лишний PNG** — S. Кадр кодируется в PNG
  (`TranslationEngine.cs:336-343`) и тут же декодируется `Cv2.ImDecode`
  (`PaddleOcrBackend.cs:199`). На 1080p это десятки мс впустую. Передавать
  `Bitmap` → `Mat` напрямую (`OpenCvSharp.Extensions.BitmapConverter.ToMat`
  или `LockBits` + `Mat.FromPixelData`). Интерфейс `IOcrBackend.ProcessFrame`
  придётся поменять (Tesseract/Windows OCR — свои конвертеры).
- [ ] **3.2. Хэш кадра через `LockBits`** вместо 4096 `GetPixel`
  (`TranslationEngine.cs:847`) — S. То же для `SampleAverageBrightness`
  (`CaptureService.cs:226`).
- [ ] **3.3. Не захватывать, пока предыдущий кадр в работе** — S. Сейчас
  `PrintWindow` делается каждые 200 мс и выбрасывается, если пайплайн занят.
- [ ] **3.4. Windows.Graphics.Capture вместо `PrintWindow`** — M. Надёжнее с
  DirectX-окнами (код сам предупреждает о чёрных кадрах —
  `CaptureService.cs:215-217`), меньше нагрузка на игру. TFM уже
  `10.0.19041`, API доступен.
- [ ] **3.5. Пакетный перевод для LLM** — M. Сейчас каждый регион —
  отдельный запрос по очереди (`TranslationService.cs:153`). Один запрос со
  всеми непереведёнными строками кадра (JSON-массив туда и обратно): в разы
  меньше задержка, реже лимиты free-tier Gemini/Groq, модель видит сцену
  целиком. Для стриминга — либо стримить весь массив, либо стримить только
  при одной строке.
- [ ] **3.6. OCR на видеокарте** — L. ONNX Runtime + DirectML с
  ONNX-моделями PaddleOCR (работает на любой видеокарте, без CUDA).

## 4. Качество перевода

- [ ] **4.1. Глоссарий в промпт LLM** — M. «Geralt → Геральт, Ciri → Цири»
  в system prompt (только правила, чьи термины есть в текущем тексте). Для
  DeepL — его собственные глоссарии через API. Для Google/MyMemory — подмена
  терминов в исходном тексте до перевода.
- [ ] **4.2. Пол персонажей** — M. Частая ошибка в русском: «я пошёл/пошла».
  Карточка персонажа в глоссарии (имя + пол) → подсказка в промпт.
  `RegionGrouper` уже отделяет узкое имя над репликой
  (`RegionGrouper.cs:133`) — его можно передавать как говорящего
  («Имя: реплика»).
- [ ] **4.3. Провайдер в ключе кэша** — S. Сейчас `UNIQUE(SourceText,
  TargetLanguage)` (`CacheRepository.cs:58`): после перехода с Google на
  Claude старые строки остаются гугловскими. Добавить провайдер (и модель)
  в ключ — или кнопку/хоткей «перевести заново».
- [ ] **4.4. Правка перевода вручную в «Истории»** с записью в кэш — S.
  Сейчас кривой перевод лечится только глоссарием или полной очисткой кэша.
- [ ] **4.5. Чище контекст LLM** — S. В контекст попадают кнопки меню и HUD,
  а строки из кэша не попадают. Класть только «диалоговые» регионы (длинные,
  с пунктуацией), включая кэшированные.
- [ ] **4.6. Язык источника** — S. Google вызывается с `sl=auto`
  (`GoogleFreeTranslator.cs:36`); на коротких фрагментах автоопределение
  ошибается. Передавать язык из настроек OCR/профиля, если он известен.
